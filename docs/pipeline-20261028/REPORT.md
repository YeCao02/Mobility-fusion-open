# 手机定位数据 pipeline 更新与全量成果汇总

更新日期：2026年10月28日。本文为公开汇总，详细内部技术报告另存本地。

## 轨迹生成算法

本轮统一事件时间与空间表达，处理区间、间隙、重叠与节点关系，输出可关联的七类表。将分析日归属与跨日所需上下文区分，按完整标识处理其可用日期上下文，避免机械拆日丢失边界；不表示每人每天均有观测。逐字段、关系和往返还原检查用于保持工程优化前后的结果一致。

格式合法不等于真实个人活动。上海单个异常标识按用户决定排除，不再调查或补算；384,587条记录保留原始证据，已验收成果不改写。上海展开日输入6,889,068,945条=接收6,888,684,358条+最终排除384,587条。flow接收3,503,432个标识，residence接收4,736,801个；两批人数不相加当作全局去重人数。

## 计算优化

采用列式读取、精确编码、原生热点计算、分区处理、并行校验、进程回收和断点复用。计算并发与科学规则分离，根据实际内存、系统提交余量和吞吐调节派发，资源不足时降载或保留结果后停止；成功提交的任务恢复时复用。上海最后阶段实际运行24路，全部任务与封装已完成。

|比较范围|实测结果|适用边界|
|---|---|---|
|早期固定50万用户比较|旧版约457.97秒，新版约812.73秒|该阶段更慢，保留负结果|

|上海residence最终封装|最后任务提交至正式发布约35分51秒|仅本批实测|

失败、准备、等待、恢复、校验及封装均属成本。历史CPU覆盖不完整，精确全过程CPU总量为未知，不能以零或成功任务成本填补。定位节点与线段不直接证明真实门到门出行、方式或目的。

## 存储与数据库优化

使用压缩列式文件、分区、流式处理与按需解码降低一次性内存需求，支持Parquet与DuckDB等列式查询。完整交付含七类表及验收信息，仅比较节点、线段两表不能代表完整包体积。GPU和服务型数据库的局部试验不构成全部生产替换结论。
