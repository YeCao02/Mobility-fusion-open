GPU与数据库候选的取舍

GPU距离/混合路径和真实输入显存缓存没有稳定完整收益（一个对照102.526秒对CPU缓存101.626秒），不纳入当前生产；原Numba失败也不能作为有效GPU基准。PostgreSQL/PostGIS在20万行样本上已能运行并验证索引/查询，但样本、查询与服务范围有限，未替代当前Parquet＋DuckDB生产主线，没有建立永久全量PostGIS镜像。[S01、S19]

四、存储与数据库优化：缩减完整包，保持可解释接口

  1. 先纠正长期保存范围。 旧精简生产与新增完整研究接口不是同一内容合同；一度把大量研究中间快照全量永久保存，造成结果体积目标偏离。最终r1固定七表及必要能力，研究历史、候选过程和旧端点快照不自动进入长期全量合同。投影后不保存的研究字段不能靠新reader恢复；后置投影省存储不代表此前构链CPU已省。[S01、S07、S19]
  2. Parquet唯一载荷＋DuckDB视图/轻目录。 保留本地批量研究和可移植离线查询；类型化支持区间改善可查询性，精确字典、整数/二进制身份和H3、端点引用与可验证预测/残差避免重复物理内容。不同时间列含义仍分开；并非盲目删列或把NULL恢复成有效许可。[S02、S03]
  3. 压缩/分片按完整合同计量。 较小样本里ZSTD3比Snappy约小39.5%，ZSTD9继续省4.8%但写入代价增加；103小文件比7文件增约9%并使查询变慢。不同布局/样本不混算百分比。最终保留已验收的fast_v8＋level16，而非把某单项最小体积配置直接套全量。[S02—S04]
  4. 生产目录和读器也是包的一部分。 完整包计入七表、字典、schema、catalog、reader/decoder、输入/版本/坐标合同和COMPLETE。worker在COMMIT前做关系和精确回读，最后仍验证全载荷SHA、目录和首次消费查询；将消费schema受COMPLETE绑定，避免每次查数重复扫描全目录。[S07]
  5. 缓存生命周期单独报告。 .staging、排序spill、未提交attempt和标准化事件都不等于永久轨迹结果。可复建临时件经依赖审查后回收；输入迁盘要逐文件校验并给新绑定，不批量改历史plan/hash。本轮迁移与回收精确字节数以新回执为准，不用缓存减少冒充结果压缩率。
